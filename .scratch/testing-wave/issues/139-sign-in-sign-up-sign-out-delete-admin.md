**What to build:** The account screens' fixes from waves 34 to 40 and Lee's rulings of 2026-09-26: code screens, Log In errors, password reset, sign-out, Delete account, and admins. One agent, as a list. Onboarding body copy is Xuan's and does not change; labels and error lines may.
1. **Admins get every feature (122-004).** `requirePro` in `supabase/functions/_shared/vana/entitlement.ts` reads `user_entitlements` only, so an Admin with no Pro gets 403 `pro_required`. It also reads `users.is_admin` and lets an Admin through. This supersedes mp-416's server check for admins. `pro_required` also loses its Retry in `vana_chat_screen.dart` and `vana_companion.dart`, because a retry can never pass.
2. **The admin read stops looping offline (118-003, 119-004, 120-009).** `isAdminProvider` fails and re-reads every 25-70 ms while reads fail, up to 4,421 times. Netcut keeps connectivity "online", so `_retryWhenReachable`'s network listener is not the trigger. Likely cause (unverified): the `onAuthStateChange` listener also gets the replayed last event when it subscribes. When that event's session id differs from `currentUser` (a failed offline refresh), every rebuild invalidates itself again. It invalidates only on a real user change, and a failed read re-reads once, on an offline-to-online change or on resume.
3. **A session the server ended goes to Log In (117-011).** After a global logout the app stays signed in, and Vana gets eleven 401 `unauthenticated` answers while the card stays on "Looking at your day…". On a 401 (`vana_transport.dart:205`), the app refreshes the session once. If GoTrue refuses the refresh token, it signs out locally and lands on Log In with no red screen. A retryable refresh error stays signed in. Nothing retries a 401.
4. **`public.users.created_at` is the real instant (120-003, 121-004).** `UserProfile.toJson` (`user_preferences.dart:540`) and `user_repository.dart:640` send a local `DateTime` with no offset, so PostgREST reads it as UTC: 5 h early. The 10 h case adds a second shift: Drift holds wall-clock time as a UTC epoch (unverified where it is built). Send `.toUtc().toIso8601String()` and fix the stored value. Repairing dev rows from `auth.users.created_at` is the wave lead's SQL, if wanted.
5. **Resend waits as long as the server does (121-001, 124-004).** Dev's `smtp_max_frequency` is 60 s. Verify your email counts down 30 s (`verify_email_screen.dart:54`) and Enter Reset Code has no countdown at all (`verify_reset_code_screen.dart:51`). Both count down 60 s. A 429 reads "after N seconds" from the message and counts down N, never showing a bare "Failed to resend code" (`email_auth_service.dart:599`).
6. **An old code points to the newest email (121-002).** After a Resend on this screen, a 403 on a code says only the newest email's code works. It no longer says to tap Resend.
7. **The code screen hints at an existing account (124-002).** When the address is already a confirmed account, GoTrue answers signup with a decoy user and sends nothing, so the screen can never succeed. The code screen always shows "No code? This address may already have an account" with Log in (Log in with email, address filled in). It never says whether the account exists.
8. **"Use a different email" deletes the abandoned login at once (121-003).** Fresh signups only. There is no session, so this needs a new edge function (for example `discard-signup`). It takes the `user_id` from the signup answer and the email, and deletes the auth user only when both match, `email_confirmed_at` is null, the user never signed in, and it was created within the hour. It answers the same 200 whatever happened, so it reveals nothing, and a decoy id deletes nothing. Run `/security-review` on it. The anonymous-upgrade path keeps its uid (unverified whether its parked `new_email` needs clearing).
9. **Log In with an unconfirmed email reaches the code (124-001).** `email_not_confirmed` currently reads "check your credentials". Instead the app resends the signup code and opens Verify your email for that address. A verify then continues the way signup does. Check whether the onboarding answers survive the relaunch (unverified).
10. **Log In errors sit under the form (125-002, 125-007).** The 2-second snackbar (`email_login_screen.dart:114`) becomes a line under the form that stays until the next edit. It says "wrong email or password" (`invalid_credentials`), or "no connection" (`AuthRetryableFetchException`, `SocketException`), or a general failure. The mapping lives in the auth service or `auth_exceptions.dart`, and the copy comes from the content system.
11. **Cancels stay quiet (125-003).** Closing Google's page shows "Sign in failed" (`post_onboarding_auth_screen.dart:199`). `oauth_service.dart:331` throws "Google Sign-In was cancelled", but the check at :436 looks for `sign_in_canceled` (unverified that this is the path). A typed cancel exception returns quietly with no error log. Apple's 1001 is a cancel. The simulator's `unknown` stays a failure.
12. **A verified signup goes straight to the paywall (121-011).** Verify your email pops, and Create Your Account shows its sign-up buttons for about 3 s until the handoff navigates. Create Your Account shows its busy state (no buttons) from the handoff until it navigates (the exact seam is unverified: `emailAuthHandoffProvider`, `email_signup_screen.dart:160`).
13. **A recovery session is signed out unless the new password is saved (124-003).** The right reset code signs the phone in, and Cancel, back or quitting leaves that session live. `verifyResetCode` sets a "recovery pending" marker, and `setNewPassword` clears it. Cancel or back on Set New Password signs the recovery session out. At startup, a marker still set signs out before routing, so the relaunch lands on Log In. The code step should not log RevenueCat in (unverified where that happens).
14. **Sign-out never passes through the paywall (125-001).** `SettingsController.signOut` clears the Pro status before `auth.signOut()`, so the Gate closes while the user is still signed in and the router shows `/paywall`. Supabase signs out first, then the status clears; every read already happens before the first await. `deleteAccount` uses the same order (87-003).
15. **The offline sign-out line clears Welcome's buttons (120-006).** The line sits above "I already have an account" (`welcome_screen.dart:27`) or dismisses on tap. Welcome's copy does not change.
16. **A paywall sign-out logs its source (120-007).** `signOut({source})` sends `settings_sign_out_tapped` with `source: paywall` from `paywall_screen.dart:286` and `source: settings` from Settings.
17. **Delete account needs a connection and never half-deletes (121-007, 121-009).** When `delete-user` fails or cannot be reached, `deleteAccount` stops. It skips the local wipe, RevenueCat logout and sign-out, stays signed in, and says it needs a connection (MealvanaSnackbar, content key). After a successful delete, the local sign-out makes no server call (unverified whether supabase_flutter can clear the session locally). If it cannot, the 403 counts as expected and 121-009 closes.
