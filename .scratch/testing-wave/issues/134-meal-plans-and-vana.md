**What to build:** Safe retries for three Vana writes, Browse picks landing in the Plan tab's plan, two plan-sync bugs, and Vana's wording of carbs. One agent, as a list.
1. **The server ignores a repeated Vana write (IMPROVEMENTS #82, Lee).** Ticket 129's 20 s transport timeout (`vana_transport.dart:67`) reports "needs a connection" while the edge function keeps running. A slow `log_from_plan`, `pick_meals` or `save_meal` can land after the screen said it failed, and a second tap writes it twice. `7fb086ec` narrowed this (a timed-out write pulls the plan) but did not close it. The phone makes one id per user action (a UUID, reused by that action's retry) and sends it as `requestId` in the payload of `PickMealsAction`, `LogFromPlanAction` and `SaveMealAction` (`ui_action.dart:58,308,555`; call sites `meal_plan_controller.dart:352,518`, `meal_detail_controller.dart:115`). `vana-action` claims the id before running (a new table keyed on user and request id, insert on conflict do nothing) and stores the result. A repeat returns the stored result and writes nothing; a repeat that arrives while the first is still running is refused as in progress. The table and its RLS go in a new migration (read `docs/deployment/supabase-deploy-playbook.md` first). `save_meal` also races today: `saveLibraryMeal` (`meals.ts:89`) checks, then inserts.
2. **A Browse pick from a general chat goes into the Plan tab's plan (118-004, 110-009, Lee).** In a general (not meal-planning) conversation, a Browse pick lands in the plan the Plan tab shows, or starts one, instead of a hidden conversation draft. `VanaBrowseScreen._add` sends `conversationId`, so the server (`resolvePlan` → `getConversationPlan`) makes that conversation's own draft, which the chat's plan bar does not read. For a general conversation, drop the conversation scope (server `getOrCreatePlan`) and tick from `mealPlanControllerProvider`; a second tap on a ticked card takes the meal out (`UnpickMealAction`). After Done, the chat's plan bar shows that plan with Remove (`PlanBar.onRemove`). A meal-planning conversation keeps its picks in its own draft as today; only make sure its plan bar shows them after Done (110-009, `vana_chat_screen.dart:197` reads `chatAsync.value?.draftPlan`). The same applies to the meal detail page's pick (`?pick=`, `meal_detail_screen.dart:517`). Also `/vana?c=<id>` with no `mode` opens every conversation as meal planning (`app_router.dart:1217`), so a general conversation opened by link reads "New meal plan". Take the kind from the conversation.
3. **A pull never archives a newer draft (120-002).** `MealPlanRepository.applyServerPlan` (`meal_plan_repository.dart:778-790`) archives every other local plan of the week whenever it applies a confirmed plan. It runs on every pull, not only after a confirm, so a draft started after the confirm (50390c90) is archived on the phone while dev keeps it a draft. Archive locally only at a local confirm (the `confirm_plan` ack). On a pull, each plan takes the status the server sends.
4. **After login the Plan tab waits for the first pull (120-001).** The first Plan tab frame after Log In showed this account's stale local draft (5 meals, one dev no longer has) for about a second. `MealPlanController.build` answers from Drift at once when a local row exists. Only the nothing-local case waits for the sync (`firstReadBound`, `meal_plan_controller.dart:158-168`). On the first read after a sign-in, when online, wait for the pull the same way (loading, not the stale plan). A normal launch stays local-first. (Proposal; the sign-in signal is unverified.)
5. **Day notes say "835 g of carbs" (116-012, Lee).** Ticket 130 made notes write "412g carbs" (`daynotes.ts:35` system prompt, `:138` context rewrite). Lee's wording is "835 g of carbs", never macro shorthand. Change both, and add a check on the model's output that rewrites any leftover `NNNC`/`NNNg carbs` into the ruled wording. Stored notes with "835C" (plans 666be167, 8ebeb6da on dev) keep it until they regenerate. The wave lead may set `day_notes_stale` on those two dev plans.
6. **Ask Vana reads the day's numbers right (118-008).** The general opener said "tracking well toward 419 carbs" after 464 logged, and dropped the "g". The context line reads `LOGGED TODAY 16 meals 464C` next to `TARGETS … ≥419C` (`context.ts:127-129`), and the model compares them itself. Write the comparison worked out, in words, in the context (e.g. "464 g of carbs logged, 45 g over today's 419 g target" / "… 120 g to go"). Tell the general opener (`persona.ts` `OPENERS.general`) to use that line as given and to write grams as "g of carbs".
