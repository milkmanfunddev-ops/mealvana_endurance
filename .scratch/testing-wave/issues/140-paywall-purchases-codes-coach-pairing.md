# 140: Paywall, purchases, codes, coach pairing

**What to build:** The paywall's purchase, restore and reconnect fixes, the webhook's late-expiration bug, and Lee's rulings of 2026-09-26 on giveaways and coach-code pairing. One agent, as a list.
1. **A failed purchase says so (121-005, 123-002).** `ProPaywallController.buy` (`pro_paywall_controller.dart`) treats `_service.purchase(pkg) == false` as `cancelled`. `RevenueCatService.purchase` (`ai_credits/data/revenuecat_service.dart:390`) returns false for a store error too. It returns a result that keeps cancelled apart from failed; the AI-credits path uses it too, so keep that caller right. A failed purchase ends `buy` in an error, so the paywall's listener shows `paywall.purchase_failed` (MealvanaSnackbar) with Continue live. A cancel stays quiet.
2. **One purchase per intent (121-008).** Two quick Continue taps start two purchases, and only the store refuses the second. `buy` returns at once while the controller is loading, before any await, and the button is disabled in the same frame.
3. **An offline restore says it could not check (121-006).** `SubscriptionService.restore` returns null when the store call fails. `ProPaywallController.restore` ignores that and reads the cached status, so the athlete sees "No active subscription was found". A null restore becomes an error that says the check needs a connection (new content key). It is never a verdict on the account.
4. **The paywall retries once the network is back (123-009).** After an offline launch, `paywallPlansProvider` keeps "Plans aren't available right now" with no fetch until resume. While the plans are unavailable, the paywall re-reads plans and customer info on an offline-to-online change and on a short timer, for example every 15 s while it is shown. Netcut keeps connectivity "online", so the timer is what a test sees.
5. **A late EXPIRATION keeps the new plan's renewal (123-008).** An ended monthly's EXPIRATION arrived after an Annual purchase and set `will_renew` false. `entitlementRowFor` (`revenuecat-webhook/entitlements.ts:175`) computes `will_renew` as false whenever the payload is not the end. When `payloadIsTheEnd` is false and RevenueCat's end is the stored row's end, it keeps the stored `will_renew`, so mp-679's renewal grace holds.
6. **A plan's last period reads "Ends on" (123-001).** The screen takes `willRenew` from the SDK (`subscription_service.dart:358`), and the Test Store's planned end never reaches it. First, do a device check with an App Store sandbox cancel. If that reads "Ends on <date>. It won't renew.", this is Test Store only: record it and close. If not, the screen also honours `user_entitlements.will_renew = false` for the same period end (unverified that a CANCELLATION webhook sets it).
7. **A giveaway is refused and not spent while any Pro is active (122-001).** RevenueCat's `grant_entitlement` does not extend a live promotional grant, so the second code is spent for nothing. In `redeem-code/handler.ts`, before `code_claim`, a giveaway reads the caller's `user_entitlements`. When any Pro is active (a running Grant, or a paying subscription: `active_until` later than now), it refuses with a new reason, `pro_active`: "You already have free Pro until <date>." for a Grant, "You already have Pro." for a subscription (Lee, 2026-09-26). Nothing is claimed. The app maps the reason (`code_redemption.dart:107`) to a content key with the date.
8. **A coach code pairs at once (122-002, 122-003).** `openPendingPairing` writes `status: pending`, and nothing on the phone accepts it. It becomes an open pairing: `status: active`, `accepted_at` now, `requested_by: athlete`, on both the insert and the reopen path. The answer carries the coach's name. `success_paired` reads "You're paired with <coach>.", and Coach Connection reads "Paired with <coach>" (`coach_connection_screen.dart:245` says "Connected to"). `getMyCoach` already reads active rows. The wave lead flips dev's existing code-made pending rows to active with SQL. This touches mp-535. 122-008 stays won't-fix.
9. **Redeem stays busy after a success (122-005).** `CodeEntryController` leaves loading when the answer lands, so the sheet's Redeem is live again with the spent code for 100-200 ms. Once a redemption has succeeded, Redeem stays disabled (busy) until the sheet closes.
10. **"1 day of Pro" (122-006).** `redeem_code.success_coach` and `success_giveaway` (`content_defaults.json:956-957`) say "{days} days". Add a one-day form, chosen when days is 1.
11. **The code field drops full stops (122-007).** iOS turns a double space into ". ". The field (`redeem_code_sheet.dart:187`) keeps only letters, digits and spaces through an input formatter, with smart dashes and quotes off.
