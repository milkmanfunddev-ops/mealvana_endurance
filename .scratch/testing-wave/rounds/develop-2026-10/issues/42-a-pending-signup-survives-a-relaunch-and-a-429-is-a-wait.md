**Twice at once, and after a refresh.**
- *Two launches reading one record* (a cold start racing a restore, or a relaunch before the first launch finished): each reads the same JSON and decides the same branch. A clear by one leaves the other with no record (its resume finds none: `resumePendingSignup` notes "Resume verify found no pending signup" and the screen stays put). Nothing is written at launch except clears.
- *Resume run twice* (`resume=verify` screen rebuilt): the post-frame resume runs once per State, in `initState`. A second State reads the same record and restores the same answers; the email form would open a second Verify only if the athlete had left the first, which is the intended way back.
- *A Resend during verify*: Verify disables Resend while a code is being checked, but a code can be entered while a Resend is in flight. If a code is accepted while a Resend is in flight, `verifyEmailOtp` clears the record and the Resend's `markResent` then finds no record and writes nothing. If the Resend lands first, its `markResent` moves the time and the verify then clears it. Either order ends cleared.
- *Two writers* (Create Account twice): the second Create Account inside 60 s is a 429 and writes nothing; after the gap, the second code's record replaces the first (later write wins), which is the code in the newest email.
- *The Create Account countdown across a rebuild*: the timer and `_createIn` live in the form's State, so a rebuild keeps the count; leaving the form disposes the State and cancels the timer. A new 429 replaces a running countdown. Verify's countdown on a resumed code starts from the stored send time, clamped to 0..60 s, so a clock that moved backwards cannot start it above 60.
- *Store failures*: every read, write and clear catches, notes `Pending signup store: <step> failed` (no address, no password) and answers false or empty; the caller's flow goes on as before this ticket (Welcome at launch, the form on Verify).
