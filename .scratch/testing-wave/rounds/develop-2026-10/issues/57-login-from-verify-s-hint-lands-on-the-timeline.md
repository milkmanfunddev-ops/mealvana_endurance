**What happens today (48-003).** The stack is post-onboarding (`/auth/post-onboarding`) → `/auth/email-signup` (pushed and awaited by `_handleEmailSignUp`, `post_onboarding_auth_screen.dart:412-448`, `result == true` at `:430`) → Verify your email (a `MaterialPageRoute` dialog pushed by `EmailSignupScreen._openVerify`, `email_signup_screen.dart:198-217`, awaited at `:147-163`). The hint's Log in, `VerifyEmailScreen._logIn` (`lib/features/auth/presentation/screens/verify_email_screen.dart:153-159`), discards a fresh signup (`:155` → `_discardAbandonedSignup` `:124-132`, signup codes only), clears the pending-signup record (`_abandonPendingSignup('log_in')` `:156` → `EmailAuthService.abandonPendingSignup` `email_auth_service.dart:848-849`, the local record ticket 42 writes), pops itself with `false` (`:157`) and pushes `/auth/email-login` on the router (`:158`). `email_signup_screen.dart:159-162` reads `false` as "change the address" and returns, leaving the form. The login screen's success path then sees `canPop` and does `context.pop(true)` (`lib/features/auth/presentation/screens/email_login_screen.dart:93-97`). That `true` goes to a push nobody awaits, so the athlete lands on Sign Up with Email, signed in as A. Back reaches Create Your Account. Only a relaunch reaches the Timeline.

1. **Verify says which way it was left.** Make the Verify route return an enum, e.g. `enum VerifyEmailExit { verified, differentEmail, logIn }` beside `VerifyEmailScreen`. `_verify`'s success pops `verified` (`:179`), `_useDifferentEmail` pops `differentEmail` (`:147`), and `_logIn` pops `logIn` **without** pushing the login itself (drop `:158`'s `router.push` and the `router` read at `:154`). The discard and `_abandonPendingSignup('log_in')` stay first. Each other `Navigator.pop` in the screen (grep `pop(`) maps to one of the three, or to null for a system back. Its two openers change to read the enum:
   - `EmailSignupScreen._openVerify` (`email_signup_screen.dart:198-217`) and its callers `:147-163` (a fresh Create Account) and `_reopenVerify` `:238-251` (a resumed signup, ticket 42). `verified` → `_finishCreated()` as today. `differentEmail` or null → stay on the form as today. `logIn` → item 2.
   - `EmailLoginScreen._finishVerifying` (`email_login_screen.dart:152-180`, the Log In of an unconfirmed address). `verified` → as today (`:173-180`). `logIn` → stay on this login screen with the address already filled. No second login screen is pushed, which today's `_logIn` would do.
2. **Email-signup runs the login and hands back a login, not a signup.** On `logIn`: `final loggedIn = await context.push<bool>('/auth/email-login', extra: {'email': email})` (the route reads `extra['email']`, `app_router.dart:373-381`). If it is true and mounted, `context.pop(EmailSignupResult.loggedIn)` (a second value beside `true`; name it in the screen's file). If not, stay on the form. The email-signup screen's own account-exists dialog (`_showAccountExistsDialog`, `:266-315`, its Sign In at `:300-304` pushes `/auth/email-login` and drops the result) gets the same treatment: await the push and pop `loggedIn` on true. That is the same defect, and it is a call site of the route this ticket changes.
3. **Post-onboarding finishes it as a login.** `_handleEmailSignUp` (`post_onboarding_auth_screen.dart:412-448`): on `result == EmailSignupResult.loggedIn`, `await _handOff(() => _finishLoginPreservingDraft(authProvider: 'email'))`, the path `_handleEmailLogin` already takes (`:450-458`). `_finishLoginPreservingDraft` (`:372-410`) ends in `_navigateToMain()` (`:489-520`), which does `context.go('/main')` (or `/coach-portal` on web for a coach). `go` replaces the stack, so the Verify route (already popped), email-signup, email-login and post-onboarding are all gone, and Back from the Timeline does not return to them. `/main` is a protected route that checks only the live session (`app_router.dart:255-261`), so it does not depend on the startup snapshot (56).
4. **The other `/auth/email-signup` caller drops its result.** Post-onboarding's account-exists dialog, "Use Email Instead" (`post_onboarding_auth_screen.dart:300-303`), does `context.push('/auth/email-signup')` without awaiting it. A signup from there pops `true` into nothing, and the onboarding answers are never saved. Call `_handleEmailSignUp()` there instead, so both results (`true` and `loggedIn`) are handled. The only other caller is `:421` (`_handleEmailSignUp` itself, including the `resume` path from `_resumePendingSignup` `:89-95`).

**What happens to the onboarding draft (Lee's wave-2 ruling b).** The login goes through `_finishLoginPreservingDraft`, so the draft follows the existing policy (`:358-371`). If account A has no completed profile, the draft just filled in is saved onto A (`_saveOnboardingDataAndNavigate`, `:384-391`). If A is already set up, A's settings win and the athlete is told so (`auth.post_onboarding.existing_account_settings_used`, `:395-406`), then the Timeline. That matches ruling b ("Log In on an unconfirmed account that is then verified finishes as a login and keeps the onboarding draft") and what the Log In button on Create Your Account does today. The signup's controller call `signInWithEmail` (`post_onboarding_auth_controller.dart:455-526`) writes no onboarding data; `saveAllOnboardingData` runs only inside `_saveOnboardingDataAndNavigate` (`:589`).

**The pending signup.** `abandonPendingSignup('log_in')` runs on the hint tap (`verify_email_screen.dart:156`), before the login. It clears the local record (`PendingSignupStore.clear`) so a relaunch does not reopen Verify; `pending_signup_resume_seam_test.dart:299-314` covers "abandoned since launch is not reopened". A fresh signup's unconfirmed user B is discarded (`:155`). On the anonymous-upgrade path (`otpType: emailChange`, 48-003's run) nothing server-side is discarded. The anonymous user (656d8eb7 in the run) keeps B pending in `email_change` and is orphaned once A signs in. That is 30-007 (a) and the upgrade-path leftover Lee closed with 48-002 (wontfix: the anonymous-upgrade path is being removed). Not changed here.

**Findings:** 48-003.

**Decisions:**
- The login is run from the email-signup screen, not from Verify: Verify is a `MaterialPageRoute` dialog with no caller that awaits a router push, and the screen that knows the hand-off (post-onboarding) sits under email-signup.
- One more result value (`loggedIn`) rather than a global hand-off provider (mealplanning's `emailAuthHandoffProvider`): develop already hands back through pop results (`email_login_screen.dart:173-176`).
- No analytics change. `auth_flow_completed {source: post_onboarding_login}` is already sent by the controller.

**Concurrency and refresh (every async path added).**
- A double tap on the hint: the first pops Verify; the second hits a disposed route. Guard `_logIn` with the same `_verifying`/mounted check the button already reads (`:415-417`).
- The login push awaited by email-signup: if email-signup is disposed meanwhile (a system back while Log In is open), the `mounted` check drops the result. The athlete is signed in and on whatever screen is left, the same as today's direct login without a parent.
- `_finishLoginPreservingDraft` runs under `_handOff` (`:464-472`), which keeps the screen busy. A second hand-off cannot start while one runs.
