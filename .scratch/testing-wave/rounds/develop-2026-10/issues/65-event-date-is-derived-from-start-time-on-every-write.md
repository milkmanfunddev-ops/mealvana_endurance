**What to build:** Event "Test" on test@test.com shows June 20 on the athlete's list and Event Details (both read `start_time`), but its `event_date` is July 17, and `event_date` drives the calendar dots, the carb-load nudge and every coach surface (50-004). Lee (2026-10-08): "event_date derived from start_time on every write path; one-off dev SQL re-derives existing rows; a test pins the columns together". Line numbers are from code at `f8dd9171`.

How the row got this way. The dev row was created 2026-06-17 08:58:58 and last written 08:59:29, 31 seconds later, with `start_time 2026-06-20T08:58:00.000` and `event_date 2026-07-17`. Until `e8ccda76` (2026-09-15, "editing an event's date now persists") `EventsService.updateEvent` passed the stale `event.eventDate` through, so an edit moved `start_time` and left `event_date` on the date the event was created with. The row is that bug's leftover, written three months before the fix, and nothing has rewritten it since. The same row exists six times on dev, on six accounts, with identical `created_at` and `updated_at` to the microsecond: one row copied server-side, not six app writes (no script in this repo copies `events`). Three older rows (ids `23`, `49`, `69`, 2025) are the same class; `69` has `event_date null`.

What still lets the columns drift today, and what this ticket closes:
- Only `EventsService` derives (`lib/features/events/application/events_service.dart:212` create, `:317` update). `EventsRepository.createEvent`/`updateEvent` store whatever `eventDate` they are handed, and `ProviderEventImportService` calls them directly (`lib/features/integrations/application/provider_event_import_service.dart:60, :71, :140, :150`), with `eventDate` carrying the time of day rather than a date.
- Both download mappers copy the server's `event_date` as is, so a stale server row stays stale on every device forever.
- Three writers with no live caller still set `event_date` their own way or not at all (item 3).

1. **One derivation, in the domain, applied in the repository.** Move the body of `EventsService.eventDateFromStartTime` (`events_service.dart:51-56`) to `lib/features/events/domain/event.dart` as `static DateTime? Event.dateFromStartTime(String? startTime)`, plus `Event withDerivedEventDate()` that returns `copyWith(eventDate: dateFromStartTime(startTime) ?? eventDate)`. It stays the wall-clock date written in the string (`DateTime(parsed.year, parsed.month, parsed.day)`, no `toLocal()`), which is the athlete's local date because `start_time` is stored naive local (every row on dev and prod, read-only check below). The data layer cannot import `application/`, which is why it moves. `EventsService.eventDateFromStartTime` becomes a one-line forwarder (`events_service_update_event_date_test.dart` calls it) and `:212`/`:317` keep working unchanged. In `EventsRepository`, apply `withDerivedEventDate()` at the top of `createEvent` (`lib/features/events/data/events_repository.dart:231-234`, before `_saveToDrift` at `:239`) and of `updateEvent` (`:306-310`, before `_saveToDrift` at `:315`). That one place covers the Drift row (`_saveToDrift` `:575`, `:623`), the immediate upload (`_toSupabaseJson` `:737`), the dirty upload (`uploadDirtyRecords` `:186-189`, which maps from the Drift row), the provider imports and their D-2c origin flips (`provider_event_import_service.dart:60, :140`), the athlete form and the coach-on-athlete form (`events_controller.dart:105`, `:159`, reached from `event_form_screen.dart:594, :605`), and the activity link in `macro_targets_controller.dart:2117-2128`. A row with no parseable `start_time` keeps the `eventDate` it was given.
2. **The download mappers re-derive, and say so.** `EventsRepository._mapSupabaseJsonToCompanion` (`events_repository.dart:817-821`) and `EventSyncHandler.upsertEvent` (`lib/shared/services/sync/entity_sync/event_sync_handler.dart:60-64`; used by `data_sync_service.dart:308, :497` and the coach's `syncAthleteEvents` `:119`) store `Event.dateFromStartTime(start_time) ?? event_date` instead of the server's `event_date`. Re-derive rather than flag, because a coach's device downloads the athlete's rows and cannot fix them on the server, and a flag would leave the athlete's calendar dot and the coach's date wrong on screen until someone edits the event. The corrected row is NOT marked `needs_upload`: a download path that dirties rows decides "what counts as dirty" (#70), and on a coach device it would try to upload another user's row. The server is healed by the one-off SQL (item 4), and every later write goes through item 1. D9: a sync path that quietly changes a value must write it down. In `_upsertRemoteEventsPreservingDirty` (`:99-155`) count the rows re-derived and, when the count is above zero, `await _report.note('Events download: event_date re-derived from start_time', area: 'events', data: {'count': n})` once per batch. In `upsertEvent` the same note per corrected row via `_r.note(..., area: 'sync', data: {'eventId': eventId})`. `EventSyncHandler.eventToJson` (`:137-162`, no caller in `lib/`) sends the derived date too, for consistency.
3. **The three writers with no live caller derive the same way.** `CalendarService.createEvent` (`lib/features/calendar/application/calendar_service.dart:211`) sets `eventDate = DateTime.tryParse(startTime)` with the time of day (`:232-236`) and writes it to Drift (`:246`); `CalendarService.updateEvent` (`:282-305`) writes `startTime` and never `eventDate`, so it would recreate this bug if wired up; `CalendarController.createEvent` (`lib/features/calendar/presentation/providers/calendar_controller.dart:280`) parses the same way (`:302-306`, `:320`). `CoachRepository.createEventForAthlete` (`lib/features/coach_mode/data/coach_repository.dart:1184-1230`) writes `event_date` (`:1204`, Drift `:1226`) and no `start_time` at all. None has a caller: `calendarControllerProvider.notifier` is never read in `lib/`, `CalendarService.createEvent`/`updateEvent` are reached only from it, and `CoachService.createEventForAthlete` (`coach_service.dart:481`), the repository method's only caller, is never called (`CreateEventDialog` is unreferenced; coaches create events through `EventFormScreen` with `forUserId`). Route the three calendar ones through `Event.dateFromStartTime` (`updateEvent` also writes `eventDate`). For the coach method, write `start_time` as the picked date's local midnight (`DateTime(y, m, d).toIso8601String()`, the shape `provider_event_import_service.dart:80` uses) and `event_date` derived from it. Deleting them is cleanup outside this ticket; say so in the fix notes if the agent finds a reason to.
4. **One-off dev SQL, run by the lead at the close.** `events.start_time` is `text` and `events.event_date` is `date` on dev and prod (read-only, `information_schema.columns`). Every `start_time` on dev (131 of 132 rows; one is null) and prod (135 of 135) starts `YYYY-MM-DD` and none carries an offset, so the date is the first ten characters:
   ```sql
   update events
      set event_date = left(start_time, 10)::date,
          updated_at = now()
    where start_time ~ '^\d{4}-\d{2}-\d{2}'
      and event_date is distinct from left(start_time, 10)::date;
   ```
   `is distinct from` also catches `event_date null` (row `69`); `<>` would skip it. `updated_at` moves so `EventSyncHandler.upsertEvent`'s newer-than check (`event_sync_handler.dart:44-45`) pulls the change down; item 2 corrects devices regardless. Dev before (read-only, columns `id, user_id, event_name, event_date, start_time, origin, updated_at`): 9 rows, all `origin null`: the six "Test" copies (`event_date 2026-07-17`, `start_time 2026-06-20T08:58:00.000`, `updated_at 2026-06-17 08:59:29.310184`, one of them test@test.com's `65379d67-…`), and `23` Berlin Half Marathon, `49` Saturday Long Run Workout, `69` Boston Marathon. After: the same `select count(*) … where … is distinct from …` returns 0. The unique constraint `(user_id, event_date, event_name)` that `auth_migration_service.dart:284` mentions does not exist on dev or prod: the only unique indexes are `events_pkey` and `events_id_new_unique` (both on `id`), so the update cannot collide. Prod has 6 rows in the same state (read-only count, all `origin null`); that is a question below, not part of this ticket's close.

**Findings:** 50-004 (retest of 32-010).

**Decisions:**
- `start_time` is the source and `event_date` is its derived copy. No column is dropped: the readers above and the server index `idx_events_event_date` keep working, and dropping one is a schema decision.
- The derivation sits in the repository, the one place every live writer passes through. `EventsService` keeps its calls (harmless, now redundant).
- The download path re-derives without dirtying the row (item 2). The SQL heals the server once; item 1 keeps it healed.
- No migration file: no schema changes. The data fix is the one-off SQL in item 4, run by the lead.
- `start_time` stays naive local text. Moving it to `timestamptz` is outside this ruling (ticket 39 left events naive by design).
