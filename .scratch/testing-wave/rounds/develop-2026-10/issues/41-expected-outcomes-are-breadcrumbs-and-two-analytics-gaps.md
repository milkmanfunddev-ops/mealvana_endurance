**Findings:** 30-005, 30-011, 32-007 (bugs); 31-012, 32-015 (ideas, folded in); 31-013 (investigation, documented, no code change).

**Decisions:**
- Expected-outcome taxonomy: an athlete's choice (cancel, existing account, wrong password, unconfirmed address) and network weather (offline, timeout, handshake, reset) are breadcrumbs at the named sites. Real failures still report once, with their area.
- **Conflict with the 2026-10-05 policy, flagged for Lee.** `expected_failures.dart:6-8` records that since 2026-10-05 expected failures arrive as warnings "so Lee can count how often athletes are offline or failing login". This ticket follows the Findings and the lead's framing: at the sites above they become breadcrumbs, and those counts leave Sentry and Mixpanel's `error_reported`. The global downgrade-to-warning in `Report.fault` is unchanged for every other site. If Lee wants the counts kept, the helper can also send a plain Mixpanel event (`network_weather {area, expected_failure}`), which is not `error_reported`. One line in item 7; the lead asks before the wave.
- **Apple error 1000 stays a failure.** Run 30's "Apple sheet closed" was code 1000 (`AuthorizationErrorCode.unknown`) on a simulator with no Apple account. `OAuthService.isCancellation` treats only 1001 as a cancel (`oauth_service.dart:73-90`), and `oauth_cancel_is_quiet_test.dart:100` pins "the simulator's unknown stays a failure". 1000 is also what a broken Sign in with Apple capability returns. Its snackbar stays. Item 4 makes it one warning event with area auth (the needle at `expected_failures.dart:122` already downgrades it), not an area-unknown event plus a breadcrumb.
- `NoConnectionException` counts as an outcome in the auth flow: the screen already says "No connection" and the athlete can retry.
- **Lee's ruling, 2026-10-08 (closes the conflict above): keep the counts.** Every site this ticket turns into a breadcrumb (A, B, C) also sends one plain Mixpanel event `expected_failure {area, reason}`, never `error_reported`. `reason` is the weather tag (`offline`, `timeout`, `handshake`, `connection_reset`) or the auth outcome (`authOutcomeReason`: `oauth_cancelled`, `account_exists`, `oauth_account_not_found`, `wrong_credentials`, `offline` for `NoConnectionException`, `email_not_confirmed`), or `no_profile` at the push site. The weather sites send it inside `faultUnlessWeather`; the auth sites through `Report.noteExpected` (a note plus the event), beside the note.
- **One count per attempt, not per layer** (fix wave 4). The event is sent where the outcome is mapped: `EmailAuthService` (sign-in, `_failAccountCreation`) and `OAuthService` (`_expectedOutcome`). The controller's note and the Riverpod net's `auth.flow` breadcrumb do not send it again, or one wrong password would count two or three times. The seam tests assert exactly one.
- **Counts taken before analytics starts are held, not read early** (fix wave 4). The version check and the region lookup run in parallel at cold start, before consent is resolved (`app_startup_provider.dart` step 0a: the region must resolve "before anything reads consent"). Reading the tracker there would build `analyticsConsentProvider` ahead of the region answer, a privacy regression, and Mixpanel drops events before its own init anyway. So a count with no tracker in hand goes to `ExpectedFailureCounts` (cap 50) and is sent when `AppStartupService._initializeAnalytics` attaches the consent-gated tracker after `app_opened`; later ones go straight through it. No consent: the tracker is a no-op and nothing leaves. The push answer uses the same path, since it can fire before `deferred.analytics`.
- `faultUnlessWeather` returns the weather it saw (`ExpectedFailure?`), not `void`, so the version check can write its LaunchTrail line only on the weather branch.
- The two iOS offline needles sit after the RevenueCat entries, not beside the other offline ones: RevenueCat's `NETWORK_ERROR` message also says "Could not connect to the server" and must stay `store_network` (`expected_failures_test.dart` pins it).
- The four "account already linked" sites in `oauth_service.dart` (native and web) wrote a `degraded` `LoggedFault`, a warning event for an existing account. They are `info` now; the error branch writes the outcome's note and count. `refuseFreshlyMintedLoginAccount`'s `degraded` stays: it marks a minted auth user left on the server, which is a real anomaly.
- A GoTrue 500 on email sign-in: the service faults the cause and marks its `SignInFailedException` wrapper as reported (`SentryReport.markReported`); the controller reports the cause, which the identity rule turns into an "already captured" breadcrumb. One event, area auth.
- `AppStartupService.armPermissionAnswer()` (`@visibleForTesting`) holds the `configurePermissionAnswer(_storeNotificationPermission)` line the deferred chain already ran, so the test reaches the no-profile path through NotificationService's own callback. Same call, same place in the chain.
- Needles removed from `expected_failures.dart`: `AccountAlreadyExistsException` and `OAuthAccountNotFoundException`. Justified by `grep -rn "AccountAlreadyExistsException\|OAuthAccountNotFoundException" lib | grep -v auth_exceptions.dart` after the change: the only hits are throws, `is` checks and the screens' routing; no `fault`/`degraded` call reports either type, and the net breadcrumbs both. `User already registered` (GoTrue's raw text) stays. The `ExpectedFailure.accountNotFound` enum value stays (its tag may already be in Sentry).

**Concurrency and refresh (every async path this ticket added or reordered).**
- `EmailAuthService.signInWithEmail`, report then state: two taps at once each map, note and count their own result and write state last; the later finisher's state wins, as before. Two taps are two counts, which is true. Disposed mid-call: the `ref.mounted` guard skips the state write; the note and the count still go (report and tracker were read before the first await).
- `_failAccountCreation` + `_writeFailedCreation`: same shape. The note and count go before the throw; the state write is guarded.
- `OAuthService._settle`: the service is `keepAlive`, and the native sheet allows one sign-in at a time. If two overlap, each reports its own failure once (identity dedupe) and the later state write wins.
- `PostOnboardingAuthController`: `state = result` now follows the report and the analytics awaits. Concurrent calls: the later finisher wins, as before. An `invalidate` mid-call disposes the old ref, so the guarded write is skipped; the returned bool still reaches the screen.
- `deleteLog` / `restoreLog`: the event is sent from locals after the write, mounted or not. Two deletes of the same row send two events (each did reach the repository). Delete then a fast Undo: each sends its own event in completion order.
- The push answer: it can run at launch and on each resume that sees a change; each run with no profile writes one breadcrumb, one trail line and one count.
- `ExpectedFailureCounts.attach`: `_initializeAnalytics` is guarded by `_analyticsInitialized`; a retry after a failed init attaches again, which replaces the sink and flushes an already-empty buffer.
