**Decisions:**
- One fix for both Findings: the cause is a launch-time snapshot read as if it were live. A narrower fix (only the `/welcome` route) would leave 49-001's back fallback, Go Home, and 59's `_deepLinkTo` seed still landing on Welcome after an in-session login.
- The snapshot is refreshed in place (AsyncData to AsyncData), not invalidated. Invalidation re-runs the whole startup (version check, region, schema) and shows the loading screen, which is why the listener avoided it (`auth_listener_service.dart:29`).
- `root_app_widget.dart:404` already listens to `appStartupProvider`, so a refresh also releases a held notification tap. 59 owns what happens then.

**Concurrency and refresh (every async path added).**
- `refreshSession` twice at once (a `signedIn` and an `onboarding_saved` close together): give each call a sequence number and write state only if no later call has started (last caller wins). Each run reads the session at its end and skips the write (trail line) if the session user changed while it awaited `userIdProvider`.
- During startup (`build` still running): the listener's `initialSession` event does not call it (only `signedIn`/`signedOut` do). A `signedIn` that lands while `build` runs finds no data and skips with a trail line; `build` then reads the same session itself.
- After a refresh the router reads the new data on the next redirect; nothing navigates by itself.
- Sign-out then sign-in quickly: the sequence number drops the sign-out's late write.
