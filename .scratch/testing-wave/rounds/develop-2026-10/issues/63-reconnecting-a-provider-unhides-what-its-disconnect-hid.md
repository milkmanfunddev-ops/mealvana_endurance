**What to build:** A disconnect soft-hides every workout the provider imported, and the Disconnect dialog promises "They come back if you reconnect." Run 50 reconnected the same TrainingPeaks athlete and got none of the 43 back. Only a row that the next sync fetches is revived, and TrainingPeaks' sync fetches 45 days ahead, so every past workout stays hidden for good. The hide also never reached the server until Sign Out. Lee (2026-10-08): "reconnecting a provider unhides every row its disconnect hid, not only fetched matches; the hide is uploaded immediately, not at sign-out". Line numbers are from code at `f8dd9171`.

How it works today:
- Disconnect: `_disconnectProvider` (`lib/features/integrations/presentation/providers/connect_training_controller.dart:695-728`) runs `_hideProviderData` (`:756-807`), which calls `ActivitiesRepository.hideActivitiesForProviderDisconnect` (`lib/features/activities/data/activities_repository.dart:2451-2488`). That writes `hiddenByDisconnect true, needsUpload true` locally (`:2464-2470`) and uploads nothing. For Garmin it also sets `garmin_health_data.hidden_by_disconnect = true` on the server (`connect_training_controller.dart:774-786`).
- Revive: only through change detection. `ChangeDetectionService.detectChanges` puts a fetched workout whose local row is hidden into `unhiddenActivities` (`lib/features/integrations/application/change_detection_service.dart:188-199`), and the sync applies it with `unhideAndUpdateFromProvider` (`activities_repository.dart:2493-2516`): TrainingPeaks at `training_peaks_sync_service.dart:296-301` (`syncWorkouts`) and `:498-503` (`syncWorkoutsByDateRange`), Final Surge at `final_surge_sync_service.dart:426-431` and `:776-781`. V.O2 (`vdot_sync_service.dart:132-150`) and Runna (`runna_sync_service.dart:168-210`) never read `unhiddenActivities`, so their hidden rows never come back even when fetched. Garmin activities revive only server-side when a completion matches (`supabase/functions/_shared/garmin/activity_completion.ts:329`), and nothing clears the Garmin wellness flag.
- TrainingPeaks' window: Sync Now runs `syncAll` (`training_peaks_sync_service.dart:745-753`) → `syncWorkouts(userId, numDays: 45)` (`:119-122`, cap `_maxWorkoutDays` `:111`), which fetches the next 45 days only. Run 50's 43 rows are dated 2026-02-03 to 2026-09-24, all in the past.
- Why the hide waited for Sign Out: no upload follows the disconnect. The next upload chance is `_importWorkouts`, which uploads dirty activities only when `newWorkouts > 0 || updated > 0` (`connect_training_controller.dart:1841-1873`). Run 50's Sync Now imported 0 and updated 0, so `uploadDirtyRecords` never ran. When it does run there, the result is read only inside `kDebugMode` (`:1855-1864`), so a failed upload (`UploadResult.failed`, `activities_repository.dart:531, :552`) leaves no PROD trace. V.O2 (`:1315-1350`) and Runna (`:1624-1640`) already upload unconditionally as the retry path and check the result; TrainingPeaks and Final Surge do not.

1. **A repository write that unhides by provider.** Add `ActivitiesRepository.unhideActivitiesForProviderReconnect({required String userId, required String provider})`, the mirror of `hideActivitiesForProviderDisconnect` (`activities_repository.dart:2451`): one Drift update over rows with `userId`, `syncedFromProvider` in `_providerLookupVariants(provider)` (`:2141-2160`), `hiddenByDisconnect = true` and `deletedAt IS NULL`, writing `hiddenByDisconnect false, needsUpload true, localUpdatedAt now` (the same companion as `unhideAndUpdateFromProvider` `:2504-2511`, without `updatedAt`, so the provider's next sync still sees its own change). It returns the count and records it with `_report.info` like the hide (`:2471-2475`). Make the hide (`:2460-2462`) match on `_providerLookupVariants` too, so the two always cover the same rows (it uses `equals(provider)` today while `getActivitiesByUserAndProvider` uses the variants).
2. **A successful connect unhides, for the same athlete.** In `_connectProvider` (`connect_training_controller.dart:600-670`), before `authenticate()` (`:628`) read the existing row with `ref.read(integrationsRepositoryProvider).getIntegration(userId, providerId)` (`integrations_repository.dart:279-288`; it returns inactive rows, and `deactivateIntegration` `:347-373` keeps `provider_athlete_id`). Keep its `providerAthleteId`. After `authenticate()` returns, compare it with `integration.providerAthleteId`, both trimmed strings. TrainingPeaks stores `profile.id` (`training_peaks_oauth_service.dart:164`; run 50's row holds `2687398`), Final Surge `tokenResponse.athleteId` (`final_surge_oauth_service.dart:117`), Garmin the Garmin user id (`garmin_oauth_service.dart:153`). When the previous id is null or empty (no earlier row), or equal, call item 1 and then item 4's upload. When it differs, skip the unhide and record `_report.note('Reconnect as a different athlete; hidden workouts stay hidden', area: providerId, data: {'hidden': n})` (D9; Lee ruled an athlete switch expected, 47's Decisions). For Garmin, also clear the wellness flag on the server: `supabaseClient.from('garmin_health_data').update({'hidden_by_disconnect': false}).eq('user_id', userId)`, best effort with `_report.integrationFailure(providerId, 'unhide_wellness', …)`, mirroring `:774-786`. Capture the deps before the awaits (`_providerDataDeps`, `:730-749`) so the unhide completes if the provider is disposed during OAuth; the state write keeps its `ref.mounted` guard (`:634`). Runna is not in `_connectProvider`: `connectRunna` (`:1438-1537`) gets the same call after its `upsertIntegration` (`:1475-1485`). Runna's disconnect deletes its row (`:1546-1549`), so there is no previous id to compare; a Runna reconnect unhides every hidden Runna row (see Decisions).
3. **The disconnect uploads the hide at once.** In `_hideProviderData`, after the hide (`:764-770`) and when `hidden > 0`, call `deps.activitiesRepo.uploadDirtyRecords(userId)` and read the result. On `!result.success`, or a throw, record `_report.degraded(…, area: 'sync', message: 'Disconnect hide upload failed; rows stay dirty for retry', extra: {'provider': providerId, 'hidden': hidden, 'error': result.error})` (D9: Sentry, PROD-readable). The rows stay `needsUpload`, so a later upload retries them. Skip the upload while `_isUsingTempUserId || _isOnboardingInProgress` (`:290, :295, :405`; the FK 23503 guard, `test/features/integrations/connect_training_upload_guard_test.dart`) and record a `note` that it was deferred.
4. **The reconnect uploads the unhide at once**, with the same call, result check, D9 record and onboarding guard as item 3.
5. **Sync Now uploads dirty activities every time, and a failure is recorded.** In `_importWorkouts` (`connect_training_controller.dart:1838-1873`), drop the `newWorkouts > 0 || updated > 0` gate (`:1843`), the same reasoning as V.O2's comment at `:1315-1322`: `uploadDirtyRecords` is also the retry path for rows an earlier write left dirty, including a hide or unhide whose upload failed. Replace the `kDebugMode`-only failure print (`:1855-1864`) with `_report.degraded` on `!uploadResult.success` (area `sync`, provider, error), keeping the debug print if wanted.

**Findings:** 50-006.

**Decisions:**
- Unhide-all on reconnect, keyed on the athlete id, replaces fetch-matching as the way rows come back. The per-match revive in TrainingPeaks and Final Surge (`unhideAndUpdateFromProvider`) stays: it applies the provider's update to a row that was hidden. V.O2 and Runna do not get that loop. After item 2, no hidden row remains for a connected provider, so a sync never meets one.
- The athlete comparison uses `integrations.provider_athlete_id`, read from the local row before the OAuth upsert overwrites it. A missing earlier id counts as the same athlete: the hidden rows belong to this Mealvana user, and on a fresh device Drift may hold hidden rows that came down from the server with no integrations row yet.
- Runna has no stored id after a disconnect. Its reconnect unhides all hidden Runna rows; a new calendar link that covers different workouts will still dedupe through change detection on its first sync.
- `updated_at` is not stamped by the unhide (item 1). The upload carries the flag by `id`/provider key (`activities_repository.dart:684-697`), and `activities.updated_at` is a wall-clock column (ticket 39's Decisions).
- Not in scope: the 14 V.O2 rows on the dev server still read `hidden_by_disconnect null` while V.O2 is disconnected (the same missing upload, from wave 3's disconnect on another simulator). The close SQL leaves them; a V.O2 reconnect would show them either way.
