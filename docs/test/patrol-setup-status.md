## The blocker — iOS configuration naming

`patrol test --flavor dev` invokes:

```
xcodebuild build-for-testing -scheme dev -configuration Debug-dev ...
```

The configuration name `Debug-dev` is hardcoded in patrol_cli at
`patrol_cli-4.3.1/lib/src/ios/ios_test_backend.dart:45`:

```dart
String createConfiguration(String? flavor) {
  if (flavor == null) {
    return xcodeName;
  }
  return '$xcodeName-$flavor';   // always {config}-{flavor}
}
```

There is no CLI flag, no `patrol.yaml` setting, no environment variable, and
no `pubspec.yaml` option to override this format. Confirmed by reading the
patrol_cli source.

This project's iOS configurations use the opposite ordering — `dev-Debug`,
`dev-Profile`, `dev-Release`, `prod-Debug`, `prod-Profile`, `prod-Release` —
so xcodebuild fails immediately:

```
xcodebuild: error: The project does not contain a configuration named 'Debug-dev'.
```

Same wall stopped whoever wrote the orphaned
`integration_test/e2e_production_readiness_test.dart` from running it.

## Resolution paths

### Option A — Rename configs to Flutter standard (recommended)

Rename the 6 flavor configurations to match Flutter's standard convention:

| Current name    | Standard name   |
|-----------------|-----------------|
| `dev-Debug`     | `Debug-dev`     |
| `dev-Profile`   | `Profile-dev`   |
| `dev-Release`   | `Release-dev`   |
| `prod-Debug`    | `Debug-prod`    |
| `prod-Profile`  | `Profile-prod`  |
| `prod-Release`  | `Release-prod`  |

What it touches:
- `ios/Runner.xcodeproj/project.pbxproj` — config names + `defaultConfigurationName`
- `ios/Runner.xcodeproj/xcshareddata/xcschemes/{Runner,dev,prod}.xcscheme` —
  `buildConfiguration` references in build/test/profile/launch/analyze actions
- `ios/Pods/Target Support Files/Pods-*/*.xcconfig` — regenerated by
  `pod install` once project configs are renamed
- `codemagic.yaml` — search for `dev-Debug`, `dev-Release`, `prod-Release`,
  etc. and update
- `ios/dev-Debug.xcconfig`, `ios/dev-Profile.xcconfig`, etc. files in
  `ios/Flutter/` — rename the files themselves, update internal `#include`
  references

A small Ruby script analogous to `add_patrol_uitest_target.rb` can do the
project-side rename programmatically. Pods regenerate on next `pod install`.

### Option B — Add parallel configurations (CHOSEN, 2026-05-12)

Keep `dev-Debug` etc. AND add `Debug-dev` etc. alongside, all pointing at
the same underlying xcconfig. Maintenance burden grows linearly if all six
flavor-first names are added, but for the patrol smoke test only `Debug-dev`
is strictly required, so we added just that one (10 configs total).

What it touched:
- `ios/Runner.xcodeproj/project.pbxproj` — one new `XCBuildConfiguration`
  named `Debug-dev` on PBXProject + Runner + RunnerUITests, each cloning
  build settings + `baseConfigurationReference` from the existing
  `dev-Debug` configuration.

What it did NOT touch:
- Schemes (patrol's `xcodebuild -configuration Debug-dev` overrides the
  scheme's default — no scheme edit needed).
- `ios/Flutter/*.xcconfig` (reused unchanged).
- `codemagic.yaml`.
- `Pods` (will regenerate automatically on next `pod install`).

Script: `scripts/add_debug_dev_alias_config.rb` (idempotent — safe to
re-run; adds Debug-dev only if missing).

If we later want patrol to run on prod or release builds, add the
corresponding alias by extending the script — e.g. `Release-dev`,
`Debug-prod`, `Release-prod`.

### Option C — Stay on integration_test, defer Patrol

The existing `integration_test` SDK binding doesn't care about configuration
names. Tests run via `flutter test integration_test/...` which is what
Codemagic does today. Patrol's unique value (native OS dialog handling,
hot-restart between tests) isn't critical for catching app errors — those
are caught equally well by `RecordingSentryReporter` injection at test app
launch.
