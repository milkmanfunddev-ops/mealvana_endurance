## The batch — item by item

### 1. Formula: carb-target failure `CRITICAL` — NEEDS HUMAN (1 decision left)
- **Notion:** <https://app.notion.com/p/3a3e3fdb754c816dad75f84240eaa861>
- **Area:** Formula Kit / during-workout fueling. Prod 1.21.1 (104).
- **Where:** server-side edge function `supabase/functions/generate-nutrition-plan-v3/during-phase.ts`
  (+ client `nutrition_plan_service.dart`). Cascade order: personal pins → template solver →
  rule solver → LP solver.
- **Status:** diagnosis confirmed line-by-line (HIGH confidence). Not built. Scoped as one change.

**Two distinct failures were filed under one ticket:**

**Failure Mode A — the ~8g-carbs disaster (accidental, NOT gut-training).** A chain of three:
1. The template solver (which applies *both* pinned and system-default formulas) is fenced
   behind `if (gutTrainingLevel && durationMinutes > 0)` at `during-phase.ts:516`. Gut-training
   level is wrongly used as an **on/off switch** for the whole formula engine. If `gutTrainingLevel`
   is null (profile not loaded yet, coach-on-athlete, load race) the entire block is skipped.
   Client sends it conditionally (`nutrition_plan_service.dart:196-197`), sourced from
   `userProfile?.gutTraining.name` (`macro_targets_controller.dart:1909`) — a null profile drops it.
2. Execution falls through to the **rule solver** (`during-phase.ts:767-825`), which calls
   `getTemplateFoodsForPhase()` **without** `pinnedComponentNames`, so it cannot bypass the
   user's preference/allergen/diet filters the way the template loader does.
3. If those filters remove every `primary_carb` / `sports_drink` food, the solver is left with
   only electrolyte tablets. **The 8g is the incidental carb content of a couple of salt tabs** —
   not a decision the app made.

**Failure Mode B — shortfall with the formula applied (this is where gut-training lives).**
Observed 124g vs a 186g target with "4 pins honored". When a pin fires the template solver passes
`allowShortfall = true` (`during-phase.ts:646`), accepts an under-target plan, and returns
immediately (`during-phase.ts:697-711`) without topping up. Gut-training per-hour caps
(`max_per_hr_low/moderate/high` on `template_foods`; `low` applies a 0.5× multiplier) legitimately
limit how much can be added.

**The four fixes (one coherent change):**
- **Fix 1 (Mode A, critical):** decouple the template-solver guard from `gutTrainingLevel`. Run it
  whenever `durationMinutes > 0`. **Correction to original wording:** `gutTrainingLevel || 'moderate'`
  is NOT enough — an invalid-but-non-empty value like the string `'medium'` (already present in
  `macro_targets_controller.dart:800/1076/1300`, and *not* a valid `GutTraining` member) slips past
  and re-triggers the skip. Must **normalize** to a valid level. `brick-handler.ts:187-192` already
  has the correct coercion — extract and share it (also removes a duplicate).
- **Fix 2 (Mode A, client defense-in-depth):** in `nutrition_plan_service.dart`, always send
  `'gut_training_level': gutTrainingLevel ?? 'moderate'` (drop the conditional wrapper).
- **Fix 3 (Mode B, gap-fill):** after the pinned template renders, if total carbs < 90% of target,
  rule-solve the remaining deficit from the unselected food pool and append. Pins honored; gap-fill
  supplements, never replaces. **DECISION (Lee): clamp gap-fill to the gut-training per-hour cap.**
  The rule solver does *not* currently enforce that cap (only the template solver does, at
  `during-template-solver.ts:415-424`) — so the clamp must be added, or a `low`-gut athlete would be
  silently overfed. A `low`-gut athlete with a high target may still land short → that's the honest
  outcome, and it fires the shortfall card.
- **Fix 4 (observability):** surface a shortfall when the plan can't hit target. Mostly a
  **discard bug, not new work** — `MacroShortfallCard` already exists and is wired for the Before
  phase. The server already computes shortfalls for the template/pinned path
  (`collectShortfalls → during-phase.ts:706 → index.ts:367`), but they're dropped at
  `during-rule-solver.ts:521`, `during-phase.ts:818` and `:843`; the LP path never computes them;
  and client-side `nutrition_plan_mapper.dart:138-162` never reads the key. Fix = stop discarding +
  extend to rule/LP paths + read the field client-side. Route the card copy through ContentService.

**Acceptance:** a fueling plan can never ship with zero during-workout carbs for a positive-duration
workout; a null/invalid gut level no longer bypasses pins; pinned shortfalls trigger a gut-capped
gap-fill and a visible shortfall card. Deno tests for during-phase; Dart test for the always-present
payload field. **Do NOT deploy — Lee deploys the edge function separately.**

**Open decision left:** none blocking — Lee chose (a) clamp-to-cap. Ready to build.
