




Intro to Flavors and Environments
In this module, you’ll learn how to support multiple flavors and environments in your Flutter app.

But what are flavors and environments, and why do we need them?

Let’s break it down by considering the stages of app development:

Development: Code, test, repeat. You run the app directly from the IDE, using hot reload and the debugger to iterate quickly.
Testing: Quality assurance, user acceptance testing, and bug fixes happen here. The app is distributed internally so stakeholders and beta testers can download and run it on their devices.
Production: The app is live on the app stores, available to users.
All these stages are crucial to shipping a robust and high-quality app.

What Are Environments?
From an engineering perspective, it’s best practice to define separate environments so we can more easily isolate and test our software without impacting end users.

Depending on the organization and project complexity, it is common to have up to four different environments:

The four environments: development, testing, staging, and production
Each environment includes all the infrastructure needed to run the software in isolation. This may include:

Auth, Database, Storage: Separate database instances prevent test data from mixing with production data.
Analytics: Keep production analytics clean by isolating data in testing environments.
Error Monitoring: Monitor crashes and errors per environment to avoid confusion.
External Services: Use different API keys to ensure the app connects to the right backend for each environment.
For more on environments and their role within the deployment pipeline, check out the Firebase docs: Overview of environments.

What Are Flavors?
Environments are mainly related to backend infrastructure.

For the frontend, Flutter offers flavors, which are a way to build distinct versions of your app, each with different identifiers, API keys, assets, or even features.

Example showing how three variants of the same iOS app can be installed on the home screen
Flavors are particularly useful on iOS and Android since they allow multiple versions of your app to be installed simultaneously, which is extremely valuable for QA and testing purposes.

Common use cases:

Free vs. Paid: Publish different versions with distinct feature sets.
Whitelabel: Create rebranded versions for multiple clients by customizing assets, theming, etc.
One Flavor per Environment
As discussed, each environment comprises multiple services such as a database, storage, analytics, etc.

But how does your Flutter app know which environment to use?

Flavors are the answer. By matching each flavor to the corresponding environment, you can ensure your app always connects to the correct services on the backend.

What things are Flavor-specific inside a Flutter app?
Here’s a list of flavor-specific things that we will explore in this course:

App Icons and Launch Screens
Analytics
Error Monitoring
Force Update Logic
API keys for third-party services and backends
Firebase Initialization
CI Workflows
If your app needs any of these, it’s wise to set up flavors from the start. That’s why I decided to cover them early in the course.

In what cases are flavors not needed?
You may not need flavors if your app:

Doesn’t have any user-generated content that requires a remote database
Doesn’t talk to any 3rd party APIs that require different API keys for testing and production
Doesn’t use analytics or error monitoring, or if it does, you don’t care if the test and production events or logs get mixed
Doesn’t have separate free and paid versions
Doesn’t have any compile-time configurations and parameters that are read at runtime to customize your app’s behavior.
If that’s the case, you can skip this module altogether and move on to the rest of the course.

How to Add Flavors to a Flutter App
If you want to add flavors to a Flutter app, there are two techniques I recommend:

Use flutter_flavorizr: This makes the process much quicker, but it works best on a new Flutter project since it works by modifying some specific project files with a specific folder structure.
Add Flavors Manually: This is more time-consuming and error-prone, but it may be your only choice if you’re working on an existing project and need to retrofit flavors without breaking things.

The Difference Between Flavors and Dart Defines
Before we dive deeper into flavors, I want to clarify this statement from the Flutter official docs:

Flavors let you define compile-time configurations and set parameters that are read at runtime to customize your app’s behavior.

Once you’ve set up flavors, you can run your app like this:


Copy
flutter run --flavor prod
In your code, you can use the top-level appFlavor constant to customize the app behavior based on the current flavor:


Copy
// The appFlavor constant is imported from this file
import 'package:flutter/services.dart';
import 'dart:developer';
 
void main() {
  if (appFlavor == 'prod') {
    log('Running in production'),
  } else {
    log('Not running in production'),
  }
  runApp(const MainApp());
}
But there’s another way to pass compile-time configurations: using --dart-define.


Copy
flutter run --dart-define API_KEY=some-api-key
You can retrieve this value in your Dart code with String.fromEnvironment:


Copy
import 'dart:developer';
 
void main() {
  final apiKey = String.fromEnvironment('API_KEY');
  log('Do not print API keys such as this: $apiKey');
  runApp(const MainApp());
}
Key Difference: Flavors vs Dart Defines
Here’s the main distinction:

Flavors: These let you run different variants of your app and require platform-specific setup on iOS and Android. They are only supported on iOS, macOS, and Android.
Dart Defines: These are compile-time constants that affect only your Dart code and don’t require any platform-specific setup. They are supported on all platforms.
To summarize:

Flavors: Affect both your Dart code and native platform code (iOS/Android)
Dart Defines: Affect only your Dart code
As we have seen, flavors also allow you to install multiple app versions on a device, each connecting to a different environment:

Example showing how three variants of the same iOS app can be installed on the home screen
When to Use Flavors vs Dart Defines?
Use Flavors when you need to customize both your Dart code and the native iOS/Android platform side. Flavors allow you to create completely different variants of your app (e.g., separate app icons, package names, and even platform-specific configurations).
Use Dart Defines when you only need to customize your Dart code and don’t want to worry about platform setup. This is ideal for passing configuration values like API keys, environment variables, or feature flags that are purely relevant to your Dart logic.
Combining Flavors and Dart Defines
In more complex setups, you may want to combine both flavors and Dart defines. For instance, you could use flavors to separate environments (e.g., dev, prod) while using Dart defines to pass specific environment variables or configuration files, like in this example:


Copy
flutter run --flavor dev --dart-define-from-file=.env.dev
In this case:

The flavor (dev) determines platform-specific details like app icon, package name, and platform-specific services.
The dart-define-from-file passes in environment-specific variables (e.g., API_KEY, BASE_URL) to your Dart code, keeping secrets or other configuration details out of the source code.
Note about Dart Defines and API Keys
Dart defines can be used to store non-sensitive API keys in your client app (rather than hardcoding them in the source code), but they should never be used for sensitive data like secret keys. Always store secret keys securely on your server.

For details, see: How to Store API Keys in Flutter: —dart-define vs .env files.

Using Flutter Flavorizr with Custom Processors
To avoid dealing with too many changes at once, we can use custom processors.

If you read the usage section, you’ll find this:

You can also run flutter_flavorizr with a custom set of processors by appending the -p (or —processors) param followed by the processor names separated by comma:

flutter pub run flutter_flavorizr -p <processor_1>,<processor_2>

Think of processors as the various stages of the flavoring process. Knowing which ones to run is key if you want to flavor your app correctly.

As it turns out, when we run flutter_flavorizr without the -p option, all the processors are run by default, resulting in many unwanted changes to the project.

If we don’t want to mess up our existing project, we must be very specific about which processors we want to run.

Having been through this process, I can tell you that knowing which processors to run is tricky (as some of them depend on others). But after figuring it out myself, I can share my custom process for running flutter_flavorizr without going crazy.

What are xcconfig files?
Open ios/Flutter/devDebug.xcconfig and you’ll see the following:


Copy
#include? "Pods/Target Support Files/Pods-Runner/Pods-Runner.debug.xcconfig"
#include "Generated.xcconfig"
 
ASSET_PREFIX=dev
BUNDLE_NAME=Flutter Ship Dev
BUNDLE_DISPLAY_NAME=Flutter Ship Dev
The variables above are known as “User-Defined Build Settings”, and they are used inside ios/Runner.xcodeproj/project.pbxproj, which is the main Xcode project file.

Here’s a comparison of these variables across different xcconfig files:

devDebug.xcconfig
stgProfile.xcconfig
prodRelease.xcconfig

Copy
#include? "Pods/Target Support Files/Pods-Runner/Pods-Runner.debug.xcconfig"
#include "Generated.xcconfig"
 
ASSET_PREFIX=dev
BUNDLE_NAME=Flutter Ship Dev
BUNDLE_DISPLAY_NAME=Flutter Ship Dev
Old versions of Flutter Flavorizr used to add an additional FLUTTER_TARGET variable to each xcconfig file. As of Flutter Flavorizr 2.3.0, this is no longer the case.

As we can see, the variables above differ based on two things:

The build mode: which can be Debug or Release (note: Flutter profile builds use the release mode in Xcode)
The flavor: which can be dev, stg, or prod
In total, this gives us 9 combinations, and that’s why we have 9 xcconfig files.

What are Xcode schemes?
Xcode schemes are a way to define different settings for building, running, testing, profiling, and archiving your app. Each scheme corresponds to a specific way to use the app during development (such as debugging or release) or for different versions like a free or a pro edition.

Single or Multiple Entry Points?
Now that we’ve flavored our iOS app, we can install and launch completely different variants of our app on the same device:

The iOS home screen showing three versions of the app
As we have seen in the lesson about flavors vs dart-defines, we can use the appFlavor constant to detect the flavor at runtime.

This means that we can customize the behaviour and appearance of the app depending on the flavor. Example:

Settings page of the Flutter Ship iOS App (dev flavor)
It also means that we only need a single main.dart file, which is the entry point for the app.

However, there are cases where multiple main_*.dart files are necessary, such as when you add Firebase to your Flutter app and you want to import different Firebase config files depending on the flavor (we will explore this at the end of this module).

And in this lesson, we’ll explore how to create multiple main_*.dart files manually.

This lesson is optional. You only need to make the changes below for more advanced setups (e.g. when your app uses Firebase).

Creating multiple main_*.dart files
Here’s what we want to accomplish:

Multiple entry points
To do this, open lib/main.dart and rename the old main() function to runMainApp(), ensuring it now returns a Future<void>:


Copy
Future<void> runMainApp() async {
  WidgetsFlutterBinding.ensureInitialized();
  ...
}
Then, inside lib, create three files called main_dev.dart, main_stg.dart, and main_prod.dart with these contents:

main_dev.dart
main_stg.dart
main_prod.dart

Copy
import 'main.dart';
 
// * Entry point for the dev flavor
void main() async {
  await runMainApp();
}
These files call runMainApp(), which is the “real” entry point where all the app initialization takes place.

How to Simulate Flavors on Flutter Web
When working with Flutter web, you can simulate flavors using two strategies:

Multiple entry points: Define a global variable somewhere and set it for each flavor inside different main_*.dart files. This is how Flutter Flavorizr works.
Using --dart-define: Pass a flavor as a --dart-define flag and read it using String.fromEnvironment. This approach doesn’t require multiple entry points.
Trade-offs:

Multiple entry points rely on global mutable state and only work if your app has separate main_*.dart files.
--dart-define is more flexible, avoids mutable state, and allows you to pass any environment variable.
In this lesson, we’ll focus on option 2: using --dart-define for Flutter web.

Running the app on Flutter web
To run the Flutter Ship app on Chrome, use this command:


Copy

When you run this, you’ll see a warning in the console:


Copy

Flavor-related features may not function properly and could behave differently in a future release.
Don’t worry—this is just a warning, and the app will still run:

Copy

The command above fails with this error:

This means that when building for the web, you can’t use --flavor.

To work around this limitation, we can use --dart-define and pass a WEB_FLAVOR argument when running the app:

But how does the app know about WEB_FLAVOR and how to use it?

Getting the Current Flavor in Dart
To handle flavors on iOS, Android, and web, I’ve added a getFlavor() helper function in lib/env/flavor.dart:


Copy
import 'package:flutter/foundation.dart';
import 'package:flutter/services.dart';
 
enum Flavor { dev, stg, prod }
 
/// Global function to return the current flavor
Flavor getFlavor() {
  // * On iOS/Android, appFlavor is supported and set with the --flavor option
  // * On web, appFlavor is not supported so we read a separate WEB_FLAVOR
  // * variable and set it with --dart-define WEB_FLAVOR=dev|stg|prod
  const webFlavor = String.fromEnvironment('WEB_FLAVOR');
  const flavor = kIsWeb ? webFlavor : appFlavor;
  return switch (flavor) {
    'prod' => Flavor.prod,
    'stg' => Flavor.stg,
    'dev' => Flavor.dev,
    null || '' => Flavor.dev, // * if not specified or empty, default to dev
    _ => throw UnsupportedError('Invalid flavor: $flavor'),
  };
}
 
// ignore_for_file:no-equal-switch-expression-cases,avoid-nullable-interpolation
Here’s how it works:

On web, it reads the WEB_FLAVOR environment variable (set via --dart-define).
On iOS/Android, it reads the appFlavor constant (set with the --flavor option).
A switch expression is then used to check the flavor and return a (type-safe) Flavor value, or throw and exception if the flavor is invalid.

Then, getFlavor() is called whenever we need some flavor-specifi app behavior, like in the settings page:

Settings page for the Flutter Ship app on Flutter web (dev flavor)
This approach works well, but how can we ensure flavors work correctly on iOS, Android, and web?

What is a Whitelabel App?
Whitelabeling is the process of creating a generic app that can be rebranded and customized for multiple clients or customers. Essentially, you build a base app with core functionality and design, and adapt it with different themes, assets, and configurations to suit different clients’ branding and needs without having to rewrite the app from scratch for each one.

For a Flutter app, this involves customizing elements such as colors, logos, and strings, and setting up an efficient way to switch between different clients’ branding packages. The goal is to make the process of rebranding as quick and efficient as possible, often for deployment to multiple app stores under different names and appearances.

Intro to Multiple Flavors with Flutter & Firebase
If your Flutter app supports multiple flavors and connects to a Firebase backend, you need to do some extra work to ensure each flavor corresponds to a different Firebase environment.

In this scenario, it’s best to create one Firebase project for each flavor since this keeps your development, staging, and production environments separate.

Each Flutter flavor maps to a separate Firebase project
And in the coming lessons, we’ll learn how to:

create multiple Firebase projects for our Flutter Ship app
use the FlutterFire CLI to generate all the Firebase config files for each flavor
write the Dart code for initializing Firebase depending on the flavor
I’ve also included a Firebase Flavors Checklist, so you can quickly follow all the steps (without the extra explanations).

Do we really need Firebase?
Many Flutter apps don’t use Firebase at all, and I’m not trying to convince anyone to use Firebase as a backend.

However, Firebase offers services like Crashlytics, Firebase Analytics, and Firebase Remote Config, which can help you add app monitoring, feature flags, and A/B testing to your apps for free.

Specifically, we will use Firebase Analytics and Firebase Remote Config in the Flutter ship app, so the next lessons are a prerequisite for the Firebase-specific lessons in the upcoming modules.

What's hard about configuring Firebase?
When using custom backends or Dart SDKs like Supabase, you can connect to the correct environment by switching the URL and API key based on the flavor. But Firebase does not offer a Dart SDK and requires some platform-specific setup, making the flavoring process more complex.

Thankfully, the FlutterFire CLI comes to the rescue. I’ll walk you through using it to flavor your Flutter & Firebase apps without losing your mind. 😅

Why do we need FlutterFire?
Adding Firebase to a Flutter app used to be a tedious process. You’d have to manually download configuration files for each platform (like GoogleService-Info.plist for iOS and google-services.json for Android).

Now, the process is much simpler. You just run flutterfire configure and follow some interactive prompts. Once finished, these files are automatically added to your project:

lib/firebase_options.dart
ios/Runner/GoogleService-Info.plist
android/app/google-services.json
However, when working with multiple flavors, it gets trickier. You’ll need separate versions of these files for each flavor, stored in different locations to avoid overwriting them during the configuration process.

Luckily, FlutterFire 1.0.0 added support for multiple flavors (see this issue for details).

FlutterFire Config Syntax with Multiple Flavors
Let’s consider this command, which generates all the config files for the dev flavor:


Copy
flutterfire config \
  --project=flutter-ship-dev \
  --out=lib/firebase_options_dev.dart \
  --ios-bundle-id=com.codewithandrea.flutterShipApp.dev \
  --ios-out=ios/flavors/dev/GoogleService-Info.plist \
  --android-package-name=com.codewithandrea.flutter_ship_app.dev \

Here’s what each argument does:

--project: The Firebase project to use (note: pass the project ID, not the alias).
--out: Output path for the Firebase config file.
--ios-bundle-id: iOS app’s bundle ID. Find it in Xcode under Runner > General > Identity > Bundle Identifier.
--ios-out: Output path for the iOS GoogleService-Info.plist.
--android-package-name: Android app’s package name (found as applicationId in android/app/build.gradle.kts).
--android-out: Output path for the Android google-services.json.
To learn about all the available options, run flutterfire config --help.

Note that if you’re on Windows and backslashes (\) are not supported, you can remove them and run the command inline.

To use this command, you can:

Easier Setup with a Shell Script
While flutterfire config handles most of the work, you still need to run it for each flavor with different arguments.

To streamline this, I’ve included a script called flutterfire-config-template.sh at the root of the project:


Copy
#!/bin/bash
# Script to generate Firebase configuration files for different environments/flavors
# Feel free to reuse and adapt this script for your own projects
 
if [[ $# -eq 0 ]]; then
  echo "Error: No environment specified. Use 'dev', 'stg', or 'prod'."
  exit 1
fi
 
case $1 in
  dev)
    flutterfire config \
      --project=flutter-ship-dev \
      --out=lib/firebase_options_dev.dart \
      --ios-bundle-id=com.codewithandrea.flutterShipApp.dev \
      --ios-out=ios/flavors/dev/GoogleService-Info.plist \
      --android-package-name=com.codewithandrea.flutter_ship_app.dev \
      --android-out=android/app/src/dev/google-services.json
    ;;
  stg)
    flutterfire config \
      --project=flutter-ship-stg \
      --out=lib/firebase_options_stg.dart \
      --ios-bundle-id=com.codewithandrea.flutterShipApp.stg \
      --ios-out=ios/flavors/stg/GoogleService-Info.plist \
      --android-package-name=com.codewithandrea.flutter_ship_app.stg \
      --android-out=android/app/src/stg/google-services.json
    ;;
  prod)
    flutterfire config \
      --project=flutter-ship-prod \
      --out=lib/firebase_options_prod.dart \
      --ios-bundle-id=com.codewithandrea.flutterShipApp \
      --ios-out=ios/flavors/prod/GoogleService-Info.plist \
      --android-package-name=com.codewithandrea.flutter_ship_app \
      --android-out=android/app/src/prod/google-services.json
    ;;
  *)
    echo "Error: Invalid environment specified. Use 'dev', 'stg', or 'prod'."
    exit 1
    ;;
esac
If you use this script in your apps, you still need to set the correct arguments for your project, but you only need to do this once.

Then, generating all the Firebase config files becomes a breeze—no need to remember each argument.

main_prod.dart → firebase_options_prod.dart
Each main_*.dart file should do two things:

import the correct firebase_options_*.dart file
pass the config as an argument to the runMainApp function inside main.dart.
Here’s how:

main_dev.dart
main_stg.dart
main_prod.dart

Copy
import 'firebase_options_dev.dart';
import 'main.dart';
 
// * Entry point for the dev flavor
void main() async {
  await runMainApp(firebaseOptions: DefaultFirebaseOptions.currentPlatform);
}
Then, inside lib/main.dart, we can update the runMainApp function to take a FirebaseOptions argument and use it to initialize the Firebase app:


Copy
// All the imports
 
Future<void> runMainApp({required FirebaseOptions firebaseOptions}) async {
  WidgetsFlutterBinding.ensureInitialized();
  // * Initialize Firebase
  await Firebase.initializeApp(options: firebaseOptions);
  final container = ProviderContainer();
  // * Preload SharedPreferences before calling runApp, as the AppStartupWidget
  // * depends on it in order to load the themeMode
  await container.read(sharedPreferencesProvider.future);
  // run the app
  runApp(UncontrolledProviderScope(
    container: container,
    child: AppStartupWidget(
      onLoaded: (context) => const MainApp(),
    ),
  ));
}
With this setup, the Flutter app will initialize and connect to the appropriate Firebase project based on the flavor.

This is an great setup for Flutter apps with multiple flavors and Firebase! ✅

Is there an easier way?
As an alternative to the above, you could create a firebase.dart file and use a switch expression to choose the correct config based on the flavor, like in this example:


Copy
import 'package:firebase_core/firebase_core.dart';
import 'package:flutter_ship_app/env/flavor.dart';
import 'package:flutter_ship_app/firebase_options_prod.dart' as prod;
import 'package:flutter_ship_app/firebase_options_stg.dart' as stg;
import 'package:flutter_ship_app/firebase_options_dev.dart' as dev;
 
Future<void> initializeFirebaseApp() async {
  final firebaseOptions = switch (getFlavor()) {
    Flavor.prod => prod.DefaultFirebaseOptions.currentPlatform,
    Flavor.stg => stg.DefaultFirebaseOptions.currentPlatform,
    Flavor.dev => dev.DefaultFirebaseOptions.currentPlatform,
  };
  await Firebase.initializeApp(options: firebaseOptions);
}
But with this code, all three firebase_options_*.dart files are still imported! ⚠️

This means that all three files are compiled and bundled during the build process because tree-shaking doesn’t work here (the switch happens at runtime).

In theory, this could expose your development or staging environment details (which may be less secure than production) if someone reverse engineers your app.

While this might not be a big issue for apps that don’t handle sensitive data, it’s still a potential risk. By creating separate entry points for each flavor, only the correct config file is imported, eliminating this risk entirely. 👍

Instead of manually configuring Firebase for each flavor, you can now generate the necessary files for all environments with a single script, saving time and reducing the chance of mistakes.

By using multiple entry points, you can ensure that the correct Firebase configuration is included for each flavor, making this a good solution for production-grade apps.

Now, whenever you run your Flutter app, it will automatically connect to the appropriate Firebase environment—whether that’s dev, stg, or prod—ensuring your app behaves as expected in each stage of development and production.

#!/bin/bash
# Script to generate Firebase configuration files for different environments/flavors
# Feel free to reuse and adapt this script for your own projects
 
if [[ $# -eq 0 ]]; then
  echo "Error: No environment specified. Use 'dev', 'stg', or 'prod'."
  exit 1
fi
 
case $1 in
  dev)
    flutterfire config \
      --project=flutter-ship-dev \
      --out=lib/firebase_options_dev.dart \
      --ios-bundle-id=com.codewithandrea.flutterShipApp.dev \
      --ios-out=ios/flavors/dev/GoogleService-Info.plist \
      --android-package-name=com.codewithandrea.flutter_ship_app.dev \
      --android-out=android/app/src/dev/google-services.json
    ;;
  stg)
    flutterfire config \
      --project=flutter-ship-stg \
      --out=lib/firebase_options_stg.dart \
      --ios-bundle-id=com.codewithandrea.flutterShipApp.stg \
      --ios-out=ios/flavors/stg/GoogleService-Info.plist \
      --android-package-name=com.codewithandrea.flutter_ship_app.stg \
      --android-out=android/app/src/stg/google-services.json
    ;;
  prod)
    flutterfire config \
      --project=flutter-ship-prod \
      --out=lib/firebase_options_prod.dart \
      --ios-bundle-id=com.codewithandrea.flutterShipApp \
      --ios-out=ios/flavors/prod/GoogleService-Info.plist \
      --android-package-name=com.codewithandrea.flutter_ship_app \
      --android-out=android/app/src/prod/google-services.json
    ;;
  *)
    echo "Error: Invalid environment specified. Use 'dev', 'stg', or 'prod'."
    exit 1
    ;;

In some cases, you will need to re-run flutterfire configure (or the helper flutterfire-config.sh script).

After the initial running of flutterfire configure, you need to re-run the command any time that you:

Start supporting a new platform in your Flutter app.
Start using a new Firebase service or product in your Flutter app, especially if you start using sign-in with Google, Crashlytics, Performance Monitoring, or Realtime Database.
Re-running the command ensures that your Flutter app’s Firebase configuration is up-to-date and (for Android) automatically adds any required Gradle plugins to your app.
