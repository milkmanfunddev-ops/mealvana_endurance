# Dev Schema Refactor – Conversation Summary

**Date:** 2025‑11‑08 (America/Chicago)  
**Context:** Supabase Postgres schema simplification for Mealvana/Endurance DEV environment. Target: make things work first (no auth yet), then harden later.

---

## Goals
- Unify on a single user identifier and make tables consistently user‑scoped.
- Drop unused/overly complex tables and columns to simplify development.
- Replace ad‑hoc TEXT+CHECK with proper enums for finite sets.
- Prefer arrays over join tables for simple categorization.
- Keep `ALTER`-only migrations to preserve data where possible.
- Disable RLS and use permissive grants **for DEV only**.
- Standardize to simple, naive `timestamp` columns (no `timestamptz`) in future phases; keep current types where already used.

---

## Final Decisions

### Identity & Ownership
- Keep `users.id` (UUID) as the canonical user key.
- Backfill and add `user_id uuid not null` to every user‑scoped table.
- Keep `events.user_id` (ownership stays explicit on events).  
- Keep `events.activity_id` **nullable**; one event may optionally reference one activity.

### Keys & IDs
- Migrate primary keys for selected tables to `GENERATED BY DEFAULT AS IDENTITY` (bigint) via add‑new‑col/rename while preserving data:
  - `activities`, `events`, `carb_loading_plans`, `carb_loading_days`, `workout_notes`, `feature_survey_responses`.
- Maintain referential links during migrations (temp columns, data copy, FK rewire).

### Enums
- Introduced and used:
  - `gender_enum`, `distance_unit_enum`, `pace_unit_enum`, `gut_training_enum`
  - `sport_enum` (running, cycling, swimming)
  - `activity_status_enum` (planned, in_progress, completed, skipped)
  - `intensity_enum` (easy, moderate, hard, race)
  - `cycling_terrain_enum` (flat, rolling, hilly)
  - `indoor_outdoor_enum` (indoor, outdoor)
  - `cycling_goal_enum` (endurance, tempo, intervals)
  - `plan_type_enum` (standard, carb_loading, recovery)
  - `category_enum` (before_run, during_run, after_run)
- Converted applicable columns to enums (`users`, `activities`, `nutrition_plans.plan_type`, etc.).

### Arrays vs. Join Tables
- Added `category_enum[]` and `sport_enum[]` to `foods` and `user_foods` with GIN indexes.
- **Dropped** legacy suitability structure on `foods` and `user_foods`:
  - Removed JSON/boolean flags like `suitable_for_activities`, `*_suitable`, `run_portable`, `requires_preparation`, `aid_station_available`.
- **Dropped** join tables and catalogs no longer needed:
  - `food_categories`, `user_food_categories`, `carb_loading_food_meal_types`, `carb_loading_user_food_meal_types`, `categories`, `meal_types`.

### Events & Activities
- `events.user_id` retained; `events.activity_id` remains nullable.
- Added index on `events(activity_id)` (non‑unique).

### Feature Voting
- Switch constraint to **one vote per `user_id`**:
  - Backfilled `feature_survey_responses.user_id` from `device_id → users.id`.
  - Set `user_id` NOT NULL.
  - Dropped `unique_device_vote`, added `UNIQUE(user_id)`.
  - Added indexes on `user_id` and `voted_at`.

### Drops
- **Dropped tables:** `activity_completions`, `edge_functions`, `food_categories`, `user_food_categories`, `carb_loading_food_meal_types`, `carb_loading_user_food_meal_types`, `categories`, `meal_types`, `user_hidden_foods`.

### Security (DEV‑only posture)
- Disabled **RLS** across all relevant tables.
- Permissive grants to `anon`, `authenticated`, `service_role` for tables and sequences.

### Sync / Conflict
- For now, client (phone) updates should win on conflicts. Future: add `client_updated_at`/`local_updated_at` arbitration rules when enabling auth+RLS.

## Open Items for Later Phases
- Consider normalizing timestamps (consistently `timestamp` vs `timestamptz`) across all tables.
- Add partial unique index for “one event per activity” **only if** you later decide to enforce it when `activity_id` is not null.
- Remove legacy columns like `device_id` from tables once all reads/writes use `user_id`.
- Re‑enable RLS, define safe policies, and reduce grants before Beta.
- Cleanup remaining comments/triggers if any appear in future migrations.
- Add NOT NULLs/DEFAULTs and tighter FKs where the product flow is stable.
- Add application‑level constraints for arrays (e.g., allowed `category_enum` combos).

---

## Rationale Snapshot
- Speed of development outweighs auth/row‑level security at this stage.
- Enums prevent drift and reduce logic in the app.
- Arrays replace small join tables to simplify reads and client models.
- Identity PKs improve performance and UX for syncing and referencing.
- Keeping `ALTER` only avoids data loss in DEV.

---

## Acknowledged Risks (DEV only)
- Open grants + disabled RLS means no data isolation until later.
- Arrays reduce relational power; acceptable trade‑off for simplicity now.
- Identity migrations add complexity; tested path uses add/rename strategy to preserve references.
