# Design SSOT — Source Authority

**Status: RATIFIED (Xuan, 2026-08-25).** Drafted 2026-08-25; ratified the same day via the ruling desk.
**Scope:** which document owns which kind of design truth, which direction truth flows, and how a
thing that does not exist yet becomes truth. Governs everything under `spec/design/`, the ratified
reference renderings, the app repo's `lib/theme/` + `lib/shared/widgets/kyle_design/`, and the
Claude Design project *Mealvana Endurance Design System*.

This is the design analogue of the calculation SSOT's authority rule: **the QA repo ratifies;
everything else is derived or verified.** Same governance — implementation is not authorization.

## 1 · Two kinds of truth, two homes

Design truth splits along the **screenshot test** (see `design-ssot-extract`): can a side-by-side
screenshot catch a violation?

| Kind | Examples | Canonical home | Held as |
|---|---|---|---|
| **Behavior + meaning** — a screenshot cannot hold it | state machines, gestures and their data writes, suppressions, what a hue may *signify*, cross-component propagation, persistence, copy registers, number traceability | `spec/design/` (`tokens.md`, `components/`, `surfaces/`) + `conformance/design/*.gestures.yaml` | assertable rows |
| **Rendering** — a screenshot holds it exactly | hex at token resolution, radius, type scale, spacing, what a chip looks like, how the swipe *looks* mid-gesture | the **ratified reference rendering** (standalone HTML) | pixels; never re-described in prose |

Rule 1a. `spec/design/tokens.md` is the one deliberate exception: raw token values appear there
because goldens and code must resolve the same registry. No other spec file carries a raw value.

Rule 1b. Nothing in `spec/design/` describes layout, radius, or font. If a spec row could be
replaced by a screenshot, it is deleted.

## 2 · The authority map

| Artifact | Role | Source or sink | Holds |
|---|---|---|---|
| Claude Design **session** (a design conversation, with or without app screenshots) | **source** | source | **candidates** — anything, unconstrained. Starts from the library but is free to exceed it |
| `spec/design/` | **ratifying authority** | — | behavior + meaning of **ratified** things only |
| `prototypes/` repo — `prototypes/<feature>/<file>.html` | **sandbox** | source | **candidates only.** Versioned freely (`v3.html`, `v4.html`), no governance. Nothing here is truth, however often it was used |
| Ratified reference rendering — `spec/design/renderings/<name>@v<N>.html` | **pixel authority** | — | pixel truth of ratified things only. Frozen on arrival; a change is a new `@v<N+1>` file. Same precedent as `spec/fueling/*.drawer.html` |
| App repo `docs/ssot/` | verbatim mirror of the two rows above (`SSOT_SOURCE.txt` policy) | derived | never edited app-side |
| App repo `lib/theme/kyle_design/` + `lib/shared/widgets/kyle_design/` | **implementation** | derived | Dart tokens and widgets, **verified** against the reference rendering by screenshot audit |
| Claude Design **project** *Mealvana Endurance Design System* | **library** | **sink** | the ratified library only, regenerated by `/design-sync` from the app repo. Hand edits to the project are drift |

Rule 2a. The session and the project are both "Claude Design" but are different things. The
session may invent; the project may not. Conflating them is how the library drifted between
2026-05-06 and 2026-08-25.

Rule 2b. The project is regenerated, never patched. If the library is wrong, the fix lands
upstream (repo or `/qa`) and is pushed; the project is never the place a correction is first made.

Rule 2c. Kyle DeMarco's brand documents (palette PDF, Figma) are the **external source** for base
token *values*. They enter the system through `spec/design/tokens.md` (value + meaning), never
directly into code. A Kyle update is a `tokens.md` revision first.

## 3 · Candidate → ratified: the promotion path

Everything visual is in exactly one state: **candidate** or **ratified**. Only ratified things
reach `spec/design/`, the renderings folder, `kyle_design/`, or the library.

1. **Invent** — a Claude Design session produces a candidate: a new component, a new gesture, or
   a `@v<N+1>` of an existing one. No constraints. Candidates live in the session and in
   `prototypes/<feature>/` (versioned files — `v3.html`, `v4.html` — are the natural form) —
   never in `spec/design/`. **Location is the state:** everything in `prototypes/` is a
   candidate; everything in `spec/design/renderings/` is ratified.
2. **Reconcile** — `design-spec-reconcile` runs the candidate against the specs its numbers come
   from. `SPEC-ADD` and `RULING-NEEDED` findings go to their authors. A candidate may not be
   ratified with open `RULING-NEEDED` items.
3. **Ratify** — Xuan (the SSOT author) **copies** the candidate to
   `spec/design/renderings/<name>@v<N>.html`, adds a `<!-- RATIFIED <name>@v<N> <who> <date>
   from prototypes/<feature>/<file>.html -->` first line, and flips the component/surface spec
   status line to `RATIFIED v<N>`. The copy is frozen: it is never edited, only superseded by
   `@v<N+1>`. The prototype it came from stays in `prototypes/` and may keep evolving into the
   next candidate. *Liking it and using it is not ratification; the copy is.*
4. **Extract** — `design-ssot-extract` writes the behavior + meaning rows into `spec/design/`
   (a component earns `components/<name>.md` only if it has state, gesture, or meaning contracts;
   pure layout never does). Gesture rows land in `conformance/design/<surface>.gestures.yaml`.
5. **Mirror** — the QA repo is mirrored verbatim into `app/docs/ssot/` (existing policy).
6. **Implement** — the coding agent ports into `kyle_design/`, driving the reference rendering in
   a browser for gestures and screenshot-auditing its own rendering against it until identical.
   Goldens are blessed from the first correct rendering (`conformance/design/*.goldens.yaml`).
7. **Promote** — `/design-sync` regenerates the library from the app repo. The library card for
   the component *is* the ratified rendering (it arrives in `app/docs/ssot/` with the rest of the
   mirror), so library and reference cannot disagree. **This step is what was missing for the
   workout-card swipe.**

Rule 3a. A `@v<N+1>` candidate follows the same path. Ratification decides whether v<N+1>
replaces v<N> in the library or sits beside it; surfaces pin the version they compose
(`surfaces/<name>.md`), as bundles pin slices.

Rule 3b. Step 7 is not optional. A ratified thing that is not in the library is invisible to the
next session, which will re-invent it worse. That is the drift this document exists to stop.

## 4 · Triggers — when `/design-sync` must run

| Event | Where it happens | Action |
|---|---|---|
| A ratification (step 3) | `/qa` | mirror → `/design-sync` |
| Any change under `app/lib/theme/` or `app/lib/shared/widgets/kyle_design/` | app repo | `/design-sync` before the commit is considered done (add to app `CLAUDE.md` beside the `/release-cut` rule) |
| `tokens.md` revision (Kyle update or meaning ruling) | `/qa` | mirror → repo token PR → `/design-sync` |

`/design-sync` is incremental, one component at a time, never a wholesale replace. It costs
nothing in Codemagic minutes — it is a claude.ai-side write.

## 5 · Governance

- **Implementation is not authorization.** Discovering that the app or the library does X is a
  reason to log X in `DEVIATIONS.md`, never to make `spec/design/` say X.
- **A session's output is not authorization either.** A candidate the coding agent was told to
  match is still a candidate until marked. The marker is what lets promotion be mechanical.
- **Conflicts resolve by this table**, top to bottom: `spec/design/` (meaning) > ratified
  rendering (pixels) > `kyle_design/` (implementation) > library (sink). A lower row disagreeing
  with a higher one is a bug in the lower row.
- **The library's `SKILL.md` golden rules are generated content.** They quote
  `spec/design/tokens.md` and the ratified component list; they are not a second verbal truth.

**Q-SA1 — RULED (Xuan, 2026-08-25): it is a deviation to log.** The "never white" rule stands;
the app's white light-mode surfaces are recorded as `DEVIATIONS.md` D-006, status `documented`.
No token change is authorised by this ruling.

**Q-SA2 — RULED (Xuan, 2026-08-25): keep it in the system — we'll leave it until the sweep to
figure out what this color signifies.** Yolk enters `tokens.md` as a named token with a
*reserved* meaning contract; the contract is assigned at the component sweep, not before. The
app-side token (`AppColors.yolk`) may be added so widgets stop inventing yellows, but it carries
no semantic authority until the row in `tokens.md` does.

**Q-SA3 — DEFERRED (Xuan, 2026-08-25).** Macro encoding stays as implemented; no change to the
`electrolyte` contract. Re-raise with the sweep.

**Q-SA4 — RULED (Xuan, 2026-08-25): use 15 px.** Card radius is 15 px, as the library rule
states. This is a screenshot-held value (§1) and lives in the reference renderings and the app's
radius constant, not in a spec row; the ruling exists so the 15/16 split in the app is now a
defect, not a choice.

## 7 · Relationship to the calculation SSOT

Same repo, same governance, same loop. Where the calculation SSOT's executable form is
`vectors/*.json`, the design SSOT's executable forms are `conformance/design/*.goldens.yaml`
(rendering) and `*.gestures.yaml` (behavior). A design bug is written as a failing golden or
gesture row here first; the app goes green against it; the row is a permanent guard.
